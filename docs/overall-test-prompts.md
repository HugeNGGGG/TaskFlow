# 冒险者公会 Task Guild — 整体测试提示词集

> 本文档为系统整体测试提供可直接执行的测试提示词，覆盖**功能测试、集成测试、边界与异常测试、性能测试、安全测试**五大类型。每条提示词均包含：测试目标、前置条件（如需要）、测试步骤、预期结果、验收标准。
>
> 编写依据：`docs/technical-overview.md`、`docs/api.md`、`docs/acceptance-checklist.md`。

---

## 0. 通用约定（执行前必读）

### 0.1 环境准备

```bash
pnpm install
pnpm --filter @task-guild/shared build
pnpm --filter @task-guild/api prisma:generate
# 启动 PostgreSQL（Docker），并配置 apps/api/.env 的 DATABASE_URL
pnpm --filter @task-guild/api prisma:migrate
pnpm --filter @task-guild/api prisma:seed
pnpm dev:api   # http://localhost:3000/api/docs（Swagger）
pnpm dev:web   # http://localhost:5173
```

### 0.2 通用约定

| 项 | 约定 |
|---|---|
| API 基址 | `/api/v1` |
| 认证方式 | `Authorization: Bearer <JWT access token>` |
| 统一错误格式 | `{ code, message }` |
| 角色位标记 | `1` 冒险者（M+）、`2` 发布官（Mgr+）、`4` 管理员（Admin），可位或叠加 |
| 默认账号 | `admin / ChangeMe123!`（管理员）、`guildmaster`（发布官）、`adventurer1`、`adventurer2`（冒险者），密码同初始密码 |
| 实时通道 | Web：Socket.IO `/ws`（握手带 JWT）；小程序：轮询（10s） |
| 文件存储 | 附件走 presigned URL；配置 COS 直传 COS，否则本地目录 |

### 0.3 测试提示词使用方法

1. 每条提示词可直接作为一次测试任务的指令，交给测试执行人或测试 AI。
2. 先满足「前置条件」，再按「测试步骤」逐条执行，记录每一步的实际结果。
3. 将实际结果与「预期结果」逐项比对；「验收标准」为判定该用例通过/失败的硬性门槛，全部满足才视为通过。
4. 性能、安全类阈值标注「建议基线」的，需结合目标部署环境（服务器规格、并发量级）在测试前确认最终阈值。

## 1. 功能测试

### F-01 Web 账号密码登录

**测试目标**：验证账号密码登录正确签发 access token 与 refresh token，并返回用户信息。

**测试步骤**：
1. 使用 `admin / ChangeMe123!` 调用 `POST /auth/login`。
2. 使用错误密码再次调用。
3. 使用不存在的账号再次调用。
4. 解析返回的 token，检查 `GET /auth/me` 能否通过该 token 正常访问。

**预期结果**：
- 正确账密返回 access token、refresh token 与用户基本信息，HTTP 200。
- 错误密码 / 不存在账号返回 `{code, message}` 形式的业务错误（如 401），且不泄露具体原因。
- access token 可正常访问受保护接口。

**验收标准**：
- 登录成功返回双 token，`/auth/me` 返回的用户信息与实际账号一致。
- 失败场景返回统一错误格式，无敏感信息泄露，无 500 异常。

---

### F-02 Token 刷新（轮换）

**测试目标**：验证 refresh token 可换取新 access token，且旧 refresh token 失效（轮换机制）。

**测试步骤**：
1. 登录获取 refresh token R1。
2. 调用 `POST /auth/refresh` 携带 R1，观察返回。
3. 用 R1 再次调用 `/auth/refresh`。
4. 使用新 access token 访问受保护接口。

**预期结果**：
- 第一次刷新成功，返回新 access token 与新 refresh token R2。
- 用已轮换的 R1 再次刷新应失败（令牌已轮换失效）。
- 新 access token 可正常访问接口。

**验收标准**：刷新令牌轮换生效，旧令牌无法复用，异常返回统一错误格式。

---

### F-03 登出（吊销刷新令牌）

**测试目标**：验证登出后刷新令牌被吊销，无法继续刷新会话。

**测试步骤**：
1. 登录获取 refresh token。
2. 调用 `POST /auth/logout`。
3. 用该 refresh token 调用 `/auth/refresh`。

**预期结果**：登出成功返回 200；被吊销的 refresh token 刷新时返回失败。

**验收标准**：登出后会话彻底失效，无法通过刷新令牌重新获取访问权限。

---

### F-04 微信登录与绑定

**测试目标**：验证小程序 `wx.login` 登录流程、未绑定账号时返回 bindToken，以及 bindToken + 账密绑定。

**测试步骤**：
1. 用未绑定的 openid 调用 `POST /auth/wechat/login`。
2. 用已绑定的 openid 调用 `/auth/wechat/login`。
3. 用上一步获得的 bindToken 调用 `POST /auth/wechat/bind` 并传入账密。
4. 绑定后再走微信登录。

**预期结果**：
- 未绑定返回 bindToken（不直接登录）。
- 已绑定直接返回 access/refresh token。
- 绑定成功后，再次微信登录可直接登录成功。

**验收标准**：bindToken 一次性有效，绑定后 openid 与账号正确关联，重复绑定被拒绝。

### F-05 个人资料 / 头像上传 / 通知偏好

**测试目标**：验证个人资料维护、头像上传、通知偏好开关。

**测试步骤**：

2. 调用 `POST /users/me/avatar` 上传头像。
3. 调用 `PUT /users/me/notification-prefs` 修改通知开关。
4. 查询 `/auth/me` 确认变更生效。

**预期结果**：资料与偏好修改后正确持久化；头像上传成功并可正常访问。

**验收标准**：变更持久化且查询结果一致；头像支持常见格式与大小校验。

### F-06 用户管理 CRUD 与角色分配

**测试目标**：验证管理员对用户的增删改查与角色位标记分配。

**测试步骤**：
1. Admin 调用 `GET/POST/PATCH /users`、`/users/:id`。
2. Admin 调用 `PATCH /users/:id/roles` 为某用户设置位标记（如 `1|2=3` 发布官+冒险者）。
3. Admin 调用 `POST /users/:id/reset-password` 重置密码。
4. 用被分配角色登录，验证权限随之变化。

**预期结果**：CRUD 正常；角色位标记正确叠加/覆盖；重置密码后旧密码失效、新密码可登录。

**验收标准**：角色变更即时生效，权限随位标记正确变化，操作有审计/日志可追溯。

### F-07 部门管理

**验收标准**：部门 CRUD 正常，越权写操作被拦截，被删除部门不影响历史数据完整性。

### F-09 任务发布（草稿 → 发布 → 取消）

**测试目标**：验证发布官任务 CRUD 及草稿/发布/取消状态流转。

**测试步骤**：
1. Mgr+ 创建草稿任务（`POST /tasks`）。
2. 草稿状态下普通用户尝试接取。
3. Mgr+ 调用 `POST /tasks/:id/publish` 发布。
4. 发布后调用 `POST /tasks/:id/cancel` 取消。

**预期结果**：
- 草稿创建成功；草稿对普通用户不可见、不可接取（对应里程碑 M1「草稿不可见」）。
- 发布后任务在大厅可见、可接取。
- 取消后任务不可再接取，已有接取者收到状态变更。

**验收标准**：状态流转符合「草稿→发布→取消」，草稿不可见，取消后接取入口关闭且通知到位。

### F-10 任务接取 / 追加指派 / 移出 / 队长

**测试目标**：验证任务人员管理链路。

**测试步骤**：
1. 冒险者调用 `POST /tasks/:id/accept` 接取任务。
2. 重复接取同一任务。
3. Mgr+ 调用 `POST /tasks/:id/assignments/:userId` 追加指派、`DELETE` 移出。
4. Mgr+ 调用 `POST /tasks/:id/captain` 设置队长。

**预期结果**：
- 首次接取成功，人员列表正确。
- 重复接取被拒绝（不产生重复记录）。
- 追加指派/移出/设队长生效并反映在任务详情与时间线。

**验收标准**：人员管理操作正确、幂等，重复接取不产生脏数据，队长权限正确（如队长可 `submitAll`）。

**验收标准**：时间线按时间顺序完整记录，所有关键动作（发布/接取/进度/提交/审核）均留痕。

### F-12 提交与审核（通过 / 打回）

**测试目标**：验证成果提交、成员提交状态、审核通过/打回。

**测试步骤**：
1. 成员调用 `POST /tasks/:id/submissions/me` 提交成果（队长可 `submitAll`）。
2. 调用 `GET /tasks/:id/submissions` 查看成员提交状态。
3. Mgr+ 调用 `POST /tasks/:id/submissions/:userId/review` 分别「通过」与「打回」。

**预期结果**：
- 提交后状态为「待审核」，成员提交状态列表正确。
- 通过 → 任务/成员进入完成态；打回 → 回退到可重做状态。
- 每次审核动作写入时间线并触发通知。

**验收标准**：提交/审核状态机正确，通过后不可重复审核，打回后可再次提交。

**验收标准**：上传-确认-版本-下载-打包全链路可用，版本可回溯，无附件越权可见。

1. 获取附件 presigned URL，测试其有效期与签名。
2. 未授权用户尝试通过 URL 下载附件。
3. 检查接口返回是否泄露敏感字段（密码哈希、refresh token、openid 等）。

**预期结果**：presigned URL 有有效期、签名不可伪造；未授权无法下载；敏感字段不外泄。

**验收标准**：附件访问受控，presigned URL 过期后失效，敏感字段不返回给前端。

### S-04 输入安全（SQL 注入 / XSS / 命令注入）

**测试目标**：验证输入注入防护。

**测试步骤**：对登录、搜索、任务字段、评论等输入点注入 SQL/XSS/命令 payload，检查响应与数据库。

**预期结果**：注入 payload 被转义/过滤或参数化处理，不执行、不存储恶意脚本。

**验收标准**：Prisma 参数化查询防 SQL 注入，前端渲染转义防 XSS，无命令注入面。

---

### S-05 密码安全（弱密码 / 重置密码 / 暴力破解）

**测试目标**：验证密码策略与重置流程安全。

**测试步骤**：
1. 设置弱密码检查是否被拒绝。
2. 尝试暴力破解（多次错误登录）。
3. 验证重置密码流程是否需授权、是否有速率限制。

**预期结果**：弱密码被拒绝，错误登录有限流/锁定，重置密码仅 Admin 且流程安全。

**验收标准**：密码强度与暴力破解防护到位，重置流程无越权。

---

### S-06 令牌与会话安全（刷新轮换 / 登出吊销 / openid 保护）

**测试目标**：验证令牌生命周期与会话安全。

**测试步骤**：验证刷新轮换、登出吊销、bindToken 一次性、openid 不泄露。

**预期结果**：刷新令牌轮换严格，登出吊销生效，bindToken 一次性，openid 不返回给前端。

**验收标准**：令牌生命周期安全，无重放、无会话固定，openid 等敏感标识受保护。

---

### S-07 传输与日志安全（HTTPS / CORS / 日志泄露）

**测试目标**：验证传输加密、跨域策略与日志安全。

**测试步骤**：
1. 检查生产环境是否强制 HTTPS。
2. 跨域请求检查 CORS 配置。
3. 检查服务端日志是否记录密码、token、openid 等敏感信息。

**预期结果**：生产强制 HTTPS，CORS 白名单严格，日志不记录敏感信息。

**验收标准**：传输加密、CORS 配置正确、日志无敏感信息泄露。
